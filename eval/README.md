# Evaluation

End-to-end evaluation on the **test** split of [M-Drama](https://huggingface.co/datasets/yixin1121/M-Drama):
get the annotations and clips, turn them into CSVs, run the model, and score the output.

* **Inference** — `eval_drama.py` runs the model over the clips (multi-GPU, `pass@k`) and
  dumps raw generations.
* **Scoring** — `eval_llm_judge.py` scores them: multiple-choice by rule, open-ended QA and
  summary by an LLM judge (any OpenAI-compatible endpoint).

```
eval/
├── prepare_eval_data.py    # ★ M-Drama test split -> the CSVs below (+ clip path map)
├── eval_drama.py           # Inference: QA / Summary, multi-GPU DDP, pass@k
├── eval_llm_judge.py       # Scoring: MC by rule, OE / Summary by LLM-as-judge
├── data/                   # CSVs generated by prepare_eval_data.py (step 2)
└── prompts/
    ├── system_prompt.txt        # Inference system prompt (identical to the SFT one)
    ├── oe_judge_prompt.txt      # Open-ended QA judge (score 0.0 / 1.0)
    └── summary_judge_prompt.txt # Summary judge (score 1-10)
```

Everything needed is in the root `requirements.txt` (`beautifulsoup4` pulls the `<answer>`
tag out of the generation, `openai` is the judge client, `yt-dlp` fetches the clips):

```bash
pip install -r requirements.txt
```

---

## 1. Get the test set

M-Drama is **gated**: request access on the dataset page, then `huggingface-cli login`.

| split | rows | clips | used for |
|---|---|---|---|
| `train` (stage `SFT` / `SFT+RL`) | 32,361 | 8,102 | training (see `data/rl/README.md`, `sft/README.md`) |
| `test` (stage `test`) | 2,075 (1,562 MC + 513 OE) | 1,036 | **evaluation** |

The dataset ships **annotations only**. Each clip is a `(url, start_time, end_time)` cut of a
YouTube video, so fetch them first (≈1,036 clips for the test split):

```bash
python sft/data/download_videos.py --split test --output_dir data/videos
# -> data/videos/{video_id}.mp4      (video_id looks like test_video_00349)
```

> Source videos belong to their copyright holders (dataset license: CC BY-NC 4.0).
> Download for research use only.

## 2. Build the eval CSVs

```bash
python eval/prepare_eval_data.py --video_dir data/videos --output_dir eval/data
```

writes four files:

| file | rows | columns |
|---|---|---|
| `eval/data/test_qa.csv` | 2,075 | `qid`, `drama_name`, `start_time`, `end_time`, `question`, `q_type`, `candidates`, `answer` |
| `eval/data/test_summary.csv` | 1,036 | `drama_name`, `start_time`, `end_time`, `caption` |
| `eval/data/test_qa_captions.csv` | 2,075 | `qid`, `caption` |
| `eval/data/test_video_map.json` | 1,036 | `{video_id: /abs/path.mp4}` |

* `drama_name` is the clip id `eval_drama.py` looks up — it is filled with M-Drama's
  `video_id`.
* `candidates` is a JSON list (`["A. ...", "B. ..."]`); the inference script reads it back
  with `eval()`. It is `[]` for open-ended questions.
* `test_summary.csv` holds one row per clip. The test split has no dedicated summary
  annotation, so the reference is the per-clip `caption` field, which already contains the
  `<caption> / <highlights> / <summary>` blocks.
* `test_qa_captions.csv` is the *video caption* context the open-ended judge is prompted
  with (`eval_llm_judge.py --caption_csv`).

Clip lookup: pass `--video_dir data/videos` and the script resolves every clip as
`{video_dir}/{video_id}.mp4` and records the map in `test_video_map.json`. Clips missing on
disk are reported (add `--strict` to fail instead).

Already have a clip library? Any of these work:

* clips named `{video_id}.mp4` → just point `--video_dir` at it.
* clips named `{title}_{HH:MM:SS}-{HH:MM:SS}.mp4` → build the map with
  `python data/rl/prepare_rl_data.py video-map --video_dir /path/to/clips --mode timestamp`
  and pass it as `--video_map` (see below).

## 3. Merge the checkpoint (RL runs only)

RL saves FSDP shards; merge them into a plain HF checkpoint first:

```bash
python scripts/model_merger.py --local_dir <ckpt_dir>
# -> <ckpt_dir>/huggingface/   (add --hf_upload_path <repo> to push it to the Hub)
```

## 4. Inference

```bash
# QA (open-ended + multiple choice)
python eval/eval_drama.py --task qa \
    --model_path ckpt/qwen3_vl_8b_mdrama_saga/huggingface \
    --processor_path Qwen/Qwen3-VL-8B-Instruct \
    --data_path eval/data/test_qa.csv \
    --output_path results/qa/saga.json \
    --video_dir data/videos \
    --video_map eval/data/test_video_map.json

# Summary
python eval/eval_drama.py --task summary \
    --model_path ckpt/qwen3_vl_8b_mdrama_saga/huggingface \
    --processor_path Qwen/Qwen3-VL-8B-Instruct \
    --data_path eval/data/test_summary.csv \
    --output_path results/summary/saga.json \
    --video_dir data/videos \
    --video_map eval/data/test_video_map.json
```

Key arguments:

| argument | default | meaning |
|---|---|---|
| `--task` | – | `qa` or `summary` (required) |
| `--model_path` | – | checkpoint to evaluate (HF format) |
| `--processor_path` | `Qwen/Qwen3-VL-8B-Instruct` | processor / tokenizer path; **must contain `qwen3` or `qwen2.5`** — that is how the model class is picked |
| `--data_path` | – | CSV built in step 2 |
| `--video_dir` / `--video_map` | `data/videos` / – | clip lookup: the map wins, otherwise `{video_dir}/{drama_name}_{start}-{end}.mp4` |
| `--system_prompt` | `eval/prompts/system_prompt.txt` | identical to the SFT system prompt |
| `--passk` | `1` | samples per prompt; `>1` enables sampling |
| `--temperature` / `--top_p` | qa 1.0/0.95, summary 0.7/0.8 | only used when `--passk > 1` |
| `--max_new_tokens` | `2048` | generation budget |
| `--batch_size` / `--nproc_per_node` | `1` / all GPUs | per-GPU batch size and GPU count |

Videos are sampled at **192 frames @ fps 2** (fixed in `collate_fn`, matching training).

Outputs:

* `--task qa` → `{"score": <accuracy>, "details": [ ... ]}`. `score` is an exact string
  match between the extracted `<answer>` and the ground truth, so it is the MC accuracy —
  open-ended answers almost never match verbatim and are scored by the LLM judge in step 5.
* `--task summary` → a plain JSON list.

Every detail record carries `vid`, `pred`, `gt` (plus `qid` / `question` / `q_type` for QA).

## 5. Scoring

```bash
export OPENAI_API_KEY=...            # or --api_key / --base_url for a self-hosted gateway
export OPENAI_BASE_URL=...           # optional

# QA: MC is scored by rule (extract_choice), OE is sent to the judge
python eval/eval_llm_judge.py --task qa \
    --result_path results/qa/saga.json \
    --output_path judge/qa/saga.json \
    --caption_csv eval/data/test_qa_captions.csv \
    --task_type OEMC \
    --model gpt-5-mini

# Summary: every sample is sent to the judge
python eval/eval_llm_judge.py --task summary \
    --result_path results/summary/saga.json \
    --output_path judge/summary/saga.json \
    --model gpt-5-mini
```

| argument | default | meaning |
|---|---|---|
| `--task` | – | `qa` or `summary` (required) |
| `--result_path` | – | inference output of `eval_drama.py` |
| `--caption_csv` | `eval/data/test_qa_captions.csv` | QA only: `qid`/`caption` CSV used as the judge's *Video Caption* context |
| `--task_type` | `OE` | QA only: which types to score — `MC`, `OE`, or both as `OEMC` |
| `--model` | `gpt-5-mini` | one or more judge models (each gets its own output file) |
| `--max_workers` | `10` | concurrent API calls; tune to your rate limits |

Output: `judge/qa/saga_gpt-5-mini.json` — the input records plus `response`, `reviewer`
and `cost`. Notes:

* `response` is a **float `0.0`/`1.0` for MC** (rule-based, no API call) and the **raw judge
  text for OE / Summary** (`Reasoning: ... <answer>1.0</answer>` for QA,
  `<answer>7</answer>` on a 1–10 scale for summary). Parse the `<answer>` tag and average
  it yourself — the script does not aggregate.
* Requests that keep failing are marked `response = "FAILED"`; re-running resumes, because
  completed samples are read back from the existing output file and skipped.
* `--model` accepts several names, one output file per judge model.
* The script prints an estimated cost using the `model2cost` table at the top of
  `eval_llm_judge.py`; unknown models are counted as free — add yours there.

## Notes

* Summary scoring **requires the reference caption to contain a `<caption>` block** — the
  judge extracts the video caption from that tag. The test split's `caption` field does;
  the train split's does not.
* Open-ended QA scoring needs `--caption_csv`: the judge is given the reference caption as
  context so it can penalize answers that contradict the video.
* Both scripts resolve prompts relative to `eval/prompts/`, so they can be run from any
  working directory.
